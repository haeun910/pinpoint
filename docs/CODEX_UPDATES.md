# Pinpoint 멀티 에이전트 공고 갱신

자료 저장소: `haeun910/pinpoint`, 브랜치 `1015`, 자료 파일 `data/notices.json`.

## 역할

1. **공고 확인 에이전트**: 공개 웹 검색과 원문 읽기로 신규 공고 및 기존 공고 변경을 확인한다. 실제 제목·기관·지역·대상·접수 기간·원문 URL을 구조화한다. 검색만으로 확인한 정보는 원문 확인으로 표시하지 않는다.
2. **분류·필터링 에이전트**: 1의 자료를 읽고 채용·청년 지원·공모전은 IT/AI만 남긴다. AI 기업의 일반 인사·영업직은 제외한다. 청약은 분야 제한 없이 보존한다. 제목만 불명확하면 원문의 기술 직무 근거를 `roleEvidence`에 기록한다.
3. **추천 에이전트**: 2의 결과에서 신입·인턴·입문 교육을 선호하는 사용자에게 유용한 근거를 `recommendationNote`로, 확인할 조건을 `recommendationChecks`로 작성한다. 나이·학력·거주지는 모르므로 신청 가능 여부를 단정하지 않는다.

독립적인 출처 조사는 병렬로 수행하고 분류·추천에는 확인된 결과를 전달한다. 자료를 최종 저장하는 에이전트는 한 명으로 제한한다. 멀티 에이전트 기능을 사용할 수 없으면 그 제한을 보고하며 병렬 실행했다고 주장하지 않는다.

## 저장과 검증

1. GitHub `fetch_file`로 `1015`의 자료와 현재 blob SHA를 읽는다. 같은 브랜치의 이 문서와 `worker/snapshot.js`, `worker/focus.js`가 데이터 계약이다.
2. 기존 `sourceDefinitions`의 공개 출처와 웹 검색을 사용한다. 새 출처를 추가할 때 source ID, 이름, category, 실제 HTTPS URL을 등록한다.
3. 공고는 같은 ID를 유지해 병합한다. 확인 실패만으로 기존 공고를 삭제하지 않는다. 모집 마감은 명확한 접수 마감일만 사용하며 목록의 게시 종료일을 접수 마감으로 추정하지 않는다.
4. 각 공고의 필수 값: id, source, category, org, title, region, target, end(YYYY-MM-DD 또는 null), url, summary, tags(문자열 배열), checked(실제 확인 날짜 YYYY-MM-DD), verification(detail/listing/search). 원문과 sourceDefinitions의 호스트와 category가 일치해야 한다.
5. 세 역할의 자료를 `items`에 넣고 출처별 실제 확인 현황을 `sources`에 기록한다. 미조사 출처를 checked로 변경하지 않는다. 전체 `updatedAt`은 실제 저장 시각 ISO 형식. 자료 version은 1이다.
6. `normalizeSnapshot`으로 형식과 출처·분류를 검사한다. 일반 공고의 오탐, 모르는 날짜, 마감 공고를 열린 공고로 표시하는 문제를 점검한다.
7. GitHub `update_file`에 현재 blob SHA와 완성 JSON을 전달해 `1015`에 저장한다. 커밋 메시지는 예: `10월 16일 IT·AI 공고와 청약 확인 및 신입 추천 갱신`. SHA 충돌이면 다시 읽고 병합한다.
8. `fetch_file`로 다시 읽어 ID·변경 내용·SHA를 확인한다. 사이트는 이 JSON을 읽으므로 일상 자료 갱신에는 재배포가 필요 없다.

원문 확인 수준을 과장하지 않는다. 날짜와 자격을 추정하지 않는다. 제출 마감과 참가 마감이 다른 경우 요약에 구분한다. 공개 공고만 기록하고 사용자의 개인정보나 인증값은 저장하지 않는다. 변경이 없으면 불필요한 커밋·알림을 생략하고, 갱신 실패 또는 사용자 확인이 필요한 경우에 알린다.
